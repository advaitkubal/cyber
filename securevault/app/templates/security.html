Core Defensive Mechanisms

01

AES-256-GCM Authenticated Encryption at Rest

app/crypto.py

Every sensitive database field (note titles, note bodies, account usernames, passwords, URLs, and remarks) is encrypted using AES-256 in Galois/Counter Mode (GCM). A 32-byte master key is stored exclusively in .env, and a dedicated 256-bit encryption key is derived for each user via HKDF-SHA256 with an individual 16-byte random salt.

Attack Prevented: Database Exfiltration and Ciphertext Tampering. Even if an attacker dumps the SQLite database file, all data remains undecipherable blobs. Any byte manipulation triggers an InvalidTag exception, immediately aborting decryption.
02

Salted Password Hashing & Timing Attack Mitigation

app/auth.py

User passwords are never stored in plaintext. They are hashed using scrypt (with fallback to PBKDF2-HMAC-SHA256 with 600,000 iterations). Non-existent usernames execute a dummy hash comparison to equalize execution time, and accounts automatically lock for 5 minutes after 5 consecutive failed attempts.

Attack Prevented: Offline Credential Cracking, User Enumeration, and Online Brute-Force Attacks. An attacker cannot discover whether a username exists through response timing, and cannot guess passwords via automated dictionary tools.
03

Tiered IP-Based Rate Limiting

app/security.py

Endpoints are guarded by Flask-Limiter keyed by remote IP address. Limits strictly throttle abusive activity: POST /login allows 5 attempts/min, POST /register allows 5/hour, credential revelation allows 30/min, and general routes allow 200/hour. Exceeding limits returns HTTP 429 and logs an audit event.

Attack Prevented: Denial of Service (DoS), Automated Credential Stuffing, and Bulk Data Scraping. Limits slow down automated scripts to an unviable frequency.
04

SQL Injection & Cross-Site Scripting (XSS) Defenses

app/db.py & app/security.py

100% of SQLite database queries use parameterized SQL statements with ? placeholders, completely avoiding string concatenation or formatting. The frontend renders dynamic text exclusively through textContent DOM properties with Jinja2 autoescaping, reinforced by strict Content-Security-Policy, X-Content-Type-Options: nosniff, and X-Frame-Options: DENY.

Attack Prevented: SQL Injection (SQLi), Stored/Reflected Cross-Site Scripting (XSS), and Clickjacking. Attack payloads like ' OR 1=1-- or <script> are treated strictly as inert literals.
05

Hardened Session Management & CSRF Defense

app/security.py

Sessions use cryptographically signed HTTP cookies with HttpOnly and SameSite=Lax. A 15-minute sliding idle timeout is enforced both server-side and client-side. Session identifiers are refreshed on login to eliminate session fixation, and all state-changing requests require a high-entropy per-session CSRF token validated with constant-time HMAC digest comparison.

Attack Prevented: Cross-Site Request Forgery (CSRF), Session Fixation, Session Hijacking via Script Access, and Stale Unattended Browser Reuse.

Additional Security Safeguards

Insecure Direct Object Reference (IDOR) Protection

Every note and credential query enforces AND user_id = ?. Accessing another user's record returns HTTP 404 rather than 403, preventing object ID enumeration.

Tamper-Resistant Security Audit Logging

Authentication successes, failures, account lockouts, rate limit trips, and data modifications are logged to an append-only audit trail with UTC timestamps and client IPs without logging secrets.

Safe Generic Error Responses

Custom handlers catch HTTP 400, 401, 403, 404, 405, 413, 429, and 500 errors to return sanitized messages. Werkzeug stack traces and internal exceptions are suppressed entirely.
